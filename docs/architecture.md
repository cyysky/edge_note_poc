# Architecture

The UI reads real data from a real server and a real database. There is no
mock layer and no in-browser storage for notes.

## Processes

| Process                       | Port | Responsibility                                                   |
| ----------------------------- | ---- | ---------------------------------------------------------------- |
| `apps/web` (Next.js)          | 3000 | Notes page and chat page, server rendering, client interactivity |
| `apps/api` (NestJS)           | 3001 | REST API, SQLite access, chat orchestration                      |
| LFM3-Omni `llama-server`      | 8080 | Chat completions plus speech synthesis                           |
| EmbeddingGemma `llama-server` | 8091 | `/v1/embeddings` for notes search                                |

The two model servers are separate processes because one `llama-server` is
bound to one loaded model. Both are local-only and are not started by
`pnpm dev`; `scripts/serve.ps1` starts the chat model, `serve.ps1 -Embeddings`
starts the embedding model.

```
browser ──> next (3000) ──┐
   │                      ├─ rewrite /api/* ──> nest (3001) ──> SQLite (WAL)
   └── server render ─────┘                        │
                                                   ├─> llama-server (8080) chat + speech
                                                   └─> llama-server (8091) embeddings
```

The API origin is a **build-time** value (`API_BASE_URL`, default
`http://127.0.0.1:3001`). Next compiles rewrites into the build output, so
changing it requires a rebuild, not just a restart.

The API reaches the model servers only from the server process; the browser
never talks to 8080 or 8091 directly. That keeps media bytes off a second
network hop and means a model restart cannot break the web origin.

## Packages

- `packages/shared` holds the wire contract (`Note`, `NoteInput`, the chat types,
  `ApiErrorResponse`, `ERROR_CODES`) and the validators. Both apps import it, so
  a field rename is a compile error on both sides. The API validates with
  exactly the code the client uses, keeping rules in one place.
- `packages/agent` is the model layer: an OpenAI-shaped client for
  `llama-server`, the tool-calling loop, tool definitions, the notes backend and
  the EmbeddingGemma client. It has no Nest or React dependency, so the CLI, the
  API and the benchmark all run the same loop.
- `apps/api` is layered: controller -> service -> repository. The repository owns
  every SQL string, prepares statements once at construction, and always binds
  parameters. `apps/api/src/chat` is a controller over `ChatService`, which owns
  the conversation and calls `packages/agent`.
- `apps/web` renders on the server first. `page.tsx` fetches the initial list;
  `NotesView` and `ChatView` own client state and call `/api/*`.
- `apps/agent` is the notes-agent CLI. `apps/bench` measures the model on this
  machine. Neither is imported by the web app.
- `apps/web/next-env.d.ts` is generated by `next dev`/`next build`; it is
  gitignored because its contents are an implementation detail that differs
  between dev and build. `next dev` also owns the marked block in
  `apps/web/AGENTS.md` and rewrites only that region.

## Data

`apps/api/src/database` owns a single `better-sqlite3` connection with
`journal_mode = WAL`, `foreign_keys = ON` and `busy_timeout = 5000`.

Migrations are append-only and tracked by `PRAGMA user_version`. Re-running is a
no-op. Never edit a shipped migration; add a new one. The first migration creates:

```sql
CREATE TABLE notes (
  id         TEXT PRIMARY KEY,
  title      TEXT NOT NULL,
  body       TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
) STRICT;
```

`DATABASE_PATH` selects the file (`:memory:` in tests). The default,
`<cwd>/data/displayer.db`, is resolved from the process working directory, so
always pass an absolute path when the working directory is not the API package.

There is no embeddings table. `search_notes` embeds the current note corpus in
process at query time (see `docs/embeddings.md` for why).

## Chat

The conversation is **stateless on the server**. The browser owns the transcript
and posts it back with each turn; the API replays it into the agent loop. A
reload or a second tab therefore cannot corrupt a running conversation, and the
API stays a pure function of its input.

| Endpoint                  | Body              | Response                           |
| ------------------------- | ----------------- | ---------------------------------- |
| `POST /api/chat`          | `ChatRequest`     | `ChatResponse` (reply, tool trace) |
| `POST /api/chat/describe` | `DescribeRequest` | `DescribeResponse` (English text)  |
| `POST /api/chat/speech`   | `SpeechRequest`   | `audio/wav` or `audio/mpeg` bytes  |

`llama-server` ignores `modalities` on a chat completion and always answers in
text, so speech is a second explicit request. The browser asks for audio only for
turns it will play; a synthesis failure never hides the text answer.

Only the last turn may carry media. Earlier turns are replayed as text, so the
API never re-sends old images or audio, and the request body has a bound the
contract can compute exactly.

### Attachments become English text

A picture is captioned and a recording is transcribed **at attach time**, not
when the turn is sent. `ChatView` reads the file to base64, posts it to
`POST /api/chat/describe`, and shows the returned English text on the
attachment card. Send is disabled while any card is still `pending`, so a turn
can never carry an attachment whose text the model has not produced.

The text is not a preview that is thrown away. Each turn carries a `derived`
array with one entry per attachment, images first and then audio, and the API
validates that count exactly. `toUserMessage` puts the caption directly after
its image part and the transcript directly after its audio part, so the model
sees contiguous bytes-then-words instead of a paragraph detached from the media.
A later turn has no bytes; `toHistoryMessage` replays `derived` as an
`Attachments in this message:` block, which is why the model can still answer
"what was in the picture?" two turns later.

`kind: 'image' | 'audio'` is explicit because the two prompts are different:
one asks for a verbatim description of what is visible, the other for a verbatim
transcription of speech, and both answer in English. An attachment that fails to
describe still sends, with `derived: [{ text: '' }]`, and the card shows the
failure: the file was the user's choice, so it goes, but nothing invents content
the model did not report.

Media arrives three ways and converges on one path. A file pick, a webcam still
and a microphone clip all become a `File`, get read to base64 by
`readAsBase64` in `ChatView`, and land in the same `PendingMedia` list, so
the 8 MB ceiling and the attachment UI apply identically. `use-camera-stream.ts`
owns the preview stream and grabs a frame with a canvas; `audio-recorder.ts`
records raw PCM through Web Audio and writes a 16 kHz mono WAV header, because
`llama-server` cannot decode the WebM/Opus `MediaRecorder` produces.

### Body limit follows the contract

`packages/shared/src/chat.ts` derives `CHAT_MAX_BODY_BYTES` from the media
limits, the per-turn count and the history length. `configure-app.ts` sizes the
JSON parser from that same constant.

This is not incidental. Express defaults to a 100 kB JSON body. An 88 kB WAV
arrives as roughly 118 kB of base64, so the transport rejected a request the
contract allowed, **before validation ran**, and the user saw a generic failure
instead of an explanation. One constant now governs the picker, the validator and
the parser; they cannot drift apart.

### Tool calls

The model plans tool calls itself; nothing in the browser or the API names a
tool. The loop in `packages/agent/src/runner.ts` asks the model, executes every
call it requested, feeds the results back, and stops when the model answers
without a call or the step budget is spent. The visible effects (notes) persist;
the calls themselves do not. `ChatResponse.tools` is a per-request trace for the
UI, not stored state.

`NOTES_API_URL` points the agent's tools at the API. The tools call the REST API
rather than opening SQLite, so the API remains the single writer and an
agent-created note gets the same validation, ids and timestamps as one made in
the UI.

## Error contract

Every failure, framework-generated or not, is shaped by a global exception filter
into:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "...",
    "details": [{ "path": "title", "message": "..." }]
  }
}
```

`code` is `VALIDATION_FAILED`, `NOT_FOUND`, `PAYLOAD_TOO_LARGE` or
`INTERNAL_ERROR`. Clients switch on `code`, never on the HTTP status alone.

`PAYLOAD_TOO_LARGE` exists because body-parser rejects an oversized body before
any controller runs. Nest wraps that rejection as a 413, and the filter maps the
status to the code so the client can tell "your file is too big" apart from "the
server broke".
